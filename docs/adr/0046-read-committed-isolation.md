# 0046. سطح ایزوله READ COMMITTED با ترتیب صریح timeoutها

**وضعیت:** پذیرفته‌شده

**تاریخ:** ۲۰۲۶-۰۸-۱۹

## زمینه

`UnitOfWork` باید یک سطح ایزوله‌ی تراکنش دیتابیس صریح انتخاب کند. صحت طبق ADR-0026 از قفل سطری
می‌آید، نه از snapshot isolation؛ اما سطح ایزوله انتخاب‌شده باید با رفتار «بازنده صف می‌کشد، بعد
با موجودی به‌روز تصمیم می‌گیرد» سازگار باشد، نه با آن در تضاد.

## تصمیم

سطح ایزوله **READ COMMITTED** است. وقتی یک `SELECT ... FOR UPDATE` مسدودشده آزاد می‌شود، مکانیزم
`EvalPlanQual` پستگرس زیر READ COMMITTED جدیدترین سطر **commit‌شده** را می‌خواند — دقیقاً همان چیزی
که ADR-0026 می‌خواهد. علاوه‌بر این، ترتیب صریح timeoutهای session تثبیت می‌شود:
`lock_timeout (3s) < statement_timeout (10s) < idle_in_transaction_session_timeout (15s)`، تا
انتظار قفل با کد SQLState قابل‌ترجمه‌ی `55P03` شکست بخورد، نه با `57014` عمومی که از یک query کند
قابل‌تشخیص نیست.

## گزینه‌های بررسی‌شده

- **REPEATABLE READ** — رد شد: بازنده‌ی race به‌جای دیدنِ سطر تازه، با خطای serialization `40001`
  مواجه می‌شود و باید در لایه‌ی application retry کند — دقیقاً همان مدل concurrency مبتنی‌بر-retry
  که ADR-0026 با جایگزینی ADR-0017 حذف کرد، از در پشتی برمی‌گردد.
- **SERIALIZABLE** — رد شد: همان ریسک `40001` را دارد، به‌علاوه predicate lockهایی که بی‌دلیل
  outbox poller را پشت مسیر نوشتن سریالیزه می‌کنند.

## پیامدها

### مثبت

- سطح ایزوله دقیقاً رفتار مستندشده‌ی ADR-0026 را می‌دهد، بدون retry اضافه.
- ترتیب timeout صریح یعنی قفل‌های معلق همیشه با یک خطای قابل‌ترجمه شکست می‌خورند، نه یک timeout مبهم.

### منفی / بدهی فنی

- هیچ — READ COMMITTED پیش‌فرض PostgreSQL است؛ فقط باید صراحتاً در کد ثبت شود تا از تغییر پیش‌فرض
  در آینده مصون بماند.
