# 0020. Valkey به‌عنوان ذخیره‌ی توزیع‌شده

**وضعیت:** پذیرفته‌شده
**تاریخ:** ۲۰۲۶-۰۸-۱۸

## زمینه

تضمین idempotency چالش (هر `transactionId` دقیقاً یک‌بار اثر) باید زیر retry **هم‌زمان** برقرار بماند — قبل از آن‌که تراکنش دیتابیس آغاز یا تمام شود. برای این گیت سریع و اتمیک (set-if-absent) یک ذخیره‌ی in-memory با semantic اتمیک لازم است که چشم‌پوشی از crash را هم بپذیرد.

## تصمیم

**Valkey** (fork متن‌باز Redis، سازگار با پروتکل آن) به‌عنوان coordination store برای کلیدهای idempotency (ADR-0021).

## گزینه‌های بررسی‌شده

- **قفل/جست‌وجو فقط در PostgreSQL** — رد شد به‌عنوان گیت اول: گیت idempotency باید پیش از شروع کار دیتابیس ارزان و اتمیک جواب بدهد؛ ولی constraint دیتابیس همچنان سپر دفاعی دوم باقی می‌ماند (ADR-0021).
- **Redis Ltd.** — رد شد: تغییر لایسنس Redis؛ Valkey همان پروتکل را با لایسنس متن‌باز (BSD) و پشتیبانی Linux Foundation می‌دهد.
- **ذخیره‌ی توزیع‌شده‌ی درون‌فرآیندی (مثل Hazelcast)** — رد شد: سنگین‌تر از نیاز و یک سیستم clustered کامل برای یک گیت ساده.

## پیامدها

### مثبت

- SETNX اتمیک و سریع؛ سازگاری با پروتکل Redis یعنی هر client استاندارد کار می‌کند؛ بدون وابستگی لایسنسی.
