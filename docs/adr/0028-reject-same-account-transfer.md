# 0028. رد انتقال به همان حساب (`transfer(A, A, …)`)

**وضعیت:** پذیرفته‌شده
**تاریخ:** ۲۰۲۶-۰۸-۱۸

## زمینه

چالش می‌خواهد رفتار `transfer(A, A, 100, "TX-100")` صریح تعریف و در README مستند شود. چنین درخواستی از نظر مالی هیچ معنایی ندارد (مبلغ از حسابی به خودش) و در عمل تقریباً همیشه نشانه‌ی خطای client است — مثلاً swap نشدن source/destination. پذیرش بی‌صدا، باگ client را پنهان می‌کند و معنای idempotency را هم مبهم می‌کند (آیا «اجرا شده»؟).

## تصمیم

انتقال به همان حساب با **خطای validation رد می‌شود** (`source == destination` ⇒ rejection قبل از هر قفل یا تراکنش)، به‌عنوان یک قانون دامنه به‌صورت Specification (ADR-0011) که result برمی‌گرداند، نه exception. موجودی‌ها بدون تغییر می‌مانند و `transactionId` مصرف نمی‌شود (درخواست نامعتبر اصلاً «اجرا» نشده؛ retry با همان ID همان rejection را می‌گیرد).

## گزینه‌های بررسی‌شده

- **No-op موفق با موجودی بدون تغییر** — رد شد: خطای client را با پاسخ موفق پنهان می‌کند؛ ممیزی و debug را سخت می‌کند.
- **اجرا به‌عنوان debit+credit روی یک حساب** — رد شد: بی‌معنی؛ در قفل ترتیب‌دار (ADR-0026) قفل دوباره‌ی یک سطر و در outbox رویداد پوچ تولید می‌کند.

## پیامدها

### مثبت

- رفتار صریح، دفاع‌پذیر و fail-fast؛ باگ client سریع سطح می‌شود. در README (بخش انتقال به همان حساب) مستند می‌شود.

### منفی / بدهی فنی

- client باید این rejection را handle کند؛ تغییر آینده‌ی این قرارداد یک breaking change در API است.
