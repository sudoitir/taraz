# 0005. مدل‌سازی دامنه با DDD

**وضعیت:** پذیرفته‌شده
**تاریخ:** ۲۰۲۶-۰۸-۱۸

## زمینه

هسته‌ی چالش منطق دامنه است (موجودی، تراکنش، انتقال) و باید صریح و قابل‌دفاع مدل شود. قوانینی مثل «موجودی منفی ممنوع» یا «انتقال اتمیک» اگر در سرویس‌های زیرساخت پخش شوند، زیر فشار هم‌زمانی قابل‌بازبینی نیستند.

## تصمیم

مدل‌سازی با **Domain-Driven Design**: Aggregate، Value Object، Domain Service و زبان فراگیر (Ubiquitous Language). لایه‌ی `core/domain` خالص است — وابستگی صفر به framework، ORM و transport.

الگوهای الزامی دامنه:

- **ساخت فقط با builder + factory** — دورزدن invariantها با constructor خالی ممنوع است.
- **قوانین دامنه به‌صورت specification/validator** که result type برمی‌گرداند، نه throw برای مسیرهای شکستِ پیش‌بینی‌شده (مثل insufficient funds یا amount نامعتبر) — ADR-0011.
- **domain eventها فقط با factory اختصاصی** ساخته می‌شوند، نه پراکنده در کد — ADR-0009.
- **زمان و حالت ambient تزریق می‌شود** (مثلاً `Clock`)؛ خواندن از حالت سراسری/سیستمی ممنوع — دامنه deterministic و قابل‌تست می‌ماند.
- **نیاز بیرونی = interface محلی.** اگر دامنه به چیزی بیرونی نیاز دارد، interface را خودش تعریف می‌کند و adapter پیاده‌سازی می‌کند؛ دامنه هرگز نوع adapter را import نمی‌کند (قاعده‌ی سخت ADR-0006، enforce با ADR-0023).

- مرجع: https://herbertograca.com/2017/09/07/domain-driven-design/

## گزینه‌های بررسی‌شده

- **Anemic model + منطق در سرویس‌** — رد شد: قوانین دامنه در چند جا پخش و غیرقابل‌بازبینی می‌شوند.
- **Exception برای همه‌ی شکست‌ها** — رد شد: شکست‌های پیش‌بینی‌شده (amount نامعتبر، insufficient funds) مسیر عادی دامنه‌اند و باید به‌صورت result برگردند، نه جریان استثنایی.

## پیامدها

### مثبت

- قوانین دامنه (مانند «موجودی منفی ممنوع») در لایه‌ی دامنه زندگی می‌کنند، نه در سرویس‌های زیرساخت.
- دامنه بدون framework و با Clock تزریق‌شده کاملاً deterministic و قابل‌تست واحد است.

### منفی / بدهی فنی

- مدل غنی به discipline بیشتری نیاز دارد؛ وسوسه‌ی «فقط یه setter اضافه کن» باید با factory/specification جواب داده شود.
