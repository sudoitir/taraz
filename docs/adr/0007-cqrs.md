# 0007. جداسازی فرمان و پرس‌وجو (CQRS)

**وضعیت:** پذیرفته‌شده
**تاریخ:** ۲۰۲۶-۰۸-۱۸

## زمینه

عملیات تغییر حالت (credit/debit/transfer) با خواندن موجودی مسیرها و نیازهای متفاوتی دارند: سمت نوشتن به transaction، lock و idempotency نیاز دارد؛ سمت خواندن فقط باید سریع و بدون side-effect باشد.

## تصمیم

**CQRS** در لایه‌ی application — جداسازی مدل فرمان (Command) از پرس‌وجو (Query):

- **سمت نوشتن (`application/service`):** یک بسته به ازای هر use-case که handler فرمان، گام‌های ارکستراسیون و منطق compensation را در خود نگه می‌دارد. فقط به inbound/outbound port و domain وابسته است؛ هیچ قانون دامنه، جزئیات transport یا persistence این‌جا نیست — فقط ارکستراسیون portها.
- **سمت خواندن (`application/query`):** هرگز state را تغییر نمی‌دهد. به ازای هر aggregate/view یک پوشه با تعریف query، handler بدون حالت، outbound port مخصوص query-repository (که driven adapter پیاده می‌کند) و DTOهای خواندنی و pagination. نوع‌های persistence/framework به interface پورت‌ها نشت نمی‌کنند.

- مرجع: https://herbertograca.com/2017/10/19/from-cqs-to-cqrs/

## گزینه‌های بررسی‌شده

- **یک مدل مشترک برای خواندن و نوشتن** — رد شد: قرارداد خواندن را به قیود تراکنشی نوشتن گره می‌زند و بالعکس.
- **CQRS کامل با event sourcing / پایگاه‌داده‌ی جدا برای read model** — رد شد: برای دامنه‌ی تک‌موجودیِ این چالش پیچیدگی اضافی است؛ CQRS در سطح لایه‌ی application کافی است.

## پیامدها

### مثبت

- فرمان‌ها اتمیسیته و idempotency را در یک نقطه‌ی مشخص تضمین می‌کنند؛ پرس‌وجوها ساده و بدون side-effect می‌مانند.
- driving adapter سمت خواندن فقط query port را می‌بیند؛ سمت نوشتن فقط command port را (قاعده‌ی سخت ADR-0006).

### منفی / بدهی فنی

- دو مدل جدا برای نگهداری؛ برای queryهای ساده کمی boilerplate اضافه.
