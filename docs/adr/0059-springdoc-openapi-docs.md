# 0059. مستندسازی API با springdoc-openapi

**وضعیت:** پذیرفته‌شده

**تاریخ:** 2026-08-19

## زمینه

قرارداد REST پروژه فقط از روی خواندن کد قابل کشف است. ارزیاب چالش (و هر مصرف‌کننده‌ی API) باید بتواند مسیرها، schema درخواست/پاسخ، header الزامی `Idempotency-Key` و پاسخ‌های خطای typed (RFC 7807) را بدون اجرای کد ببیند و در صورت تمایل از همان صفحه درخواست واقعی بفرستد. قاعده‌ی چالش می‌گوید هر فناوری اضافه باید مسئله‌ی واقعی حل کند؛ مسئله‌ی واقعی اینجا «قابل‌کشف‌بودن قرارداد» است.

## تصمیم

- وابستگی `org.springdoc:springdoc-openapi-starter-webmvc-ui` نسخه‌ی 3.1.0 (خط سازگار با Spring Boot 4.x) به ماژول `adapters/driving/rest` اضافه می‌شود — مستندات کنار خودِ API می‌ماند و ماژول container آن را به‌ارث می‌برد.
- سند OpenAPI 3 **از روی کد تولید می‌شود**؛ هیچ فایل `openapi.yaml` دست‌نگهداردی در کار نیست.
- فقط یک bean متادیتا (`OpenApiConfiguration`) + حاشیه‌نویسی‌های کوتاه روی سه controller: عنوان/خلاصه‌ی عملیات، پارامتر header مربوط به `Idempotency-Key`، و پاسخ‌های خطای typed با schema مشترک `ProblemDetail`.
- نقاط پایانی: `/v3/api-docs` (و نسخه‌ی yaml) و Swagger UI در `/swagger-ui`.

## گزینه‌های بررسی‌شده

- **فایل `openapi.yaml` دست‌نویس** — رد شد؛ از کد جدا می‌ماند و drift می‌گیرد.
- **Spring REST Docs** — رد شد؛ خروجی از تست تولید می‌شود اما تعاملی نیست و هزینه‌ی نگهداشت بالاتری دارد.
- **افزودن وابستگی به container** — رد شد؛ کار می‌کند اما مستندات از ماژولی که API را تعریف می‌کند جدا می‌افتد.

## پیامدها

### مثبت

- قرارداد API همیشه با کد هم‌گام است؛ ارزیاب می‌تواند API را در مرورگر ببیند و اجرا کند.
- پاسخ‌های خطای RFC 7807 که از قبل وجود دارند، حالا مستند هم هستند.

### منفی / بدهی فنی

- یک وابستگی خارجی جدید به adapter اضافه می‌شود (به core نفوذ نمی‌کند؛ تست‌های ArchUnit باید سبز بمانند).
- controllerها به حاشیه‌نویسی‌های springdoc کوپل می‌شوند — آگاهانه و فقط در driving adapter.
