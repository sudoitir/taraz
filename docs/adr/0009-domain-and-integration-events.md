# 0009. رویدادمحوری: Domain Event و Integration Event

**وضعیت:** پذیرفته‌شده
**تاریخ:** ۲۰۲۶-۰۸-۱۸

## زمینه

وقوع عملیات مالی (credit/debit/transfer) باید به‌صورت رویداد قابل‌انتشار باشد — هم برای جداسازی دغدغه‌ها داخل core و هم برای اطلاع‌رسانی به بیرون از مرز سرویس. دامنه نباید به جزئیات فنی انتشار (topic، serialization) آلوده شود و مصرف‌کننده‌ی بیرونی نباید به مدل داخلی ما coupled شود.

## تصمیم

دو نوع رویداد با مرز صریح:

- **DomainEvent**: خالص، به زبان دامنه، بدون جزئیات فنی؛ فقط داخل core. تاریخ‌ها با فرمت استاندارد **ISO 8601**. ساخت فقط با factory اختصاصی (ADR-0005).
- **IntegrationEvent**: قرارداد عمومیِ بیرون از مرز سرویس؛ جدا از DomainEvent مدل و در adapter از روی آن ساخته می‌شود تا تغییر مدل داخلی، قرارداد عمومی را نشکند.

- مرجع: https://herbertograca.com/2017/10/05/event-driven-architecture/

## گزینه‌های بررسی‌شده

- **یک مدل رویداد مشترک برای داخل و بیرون** — رد شد: هر تغییر داخلی، مصرف‌کننده‌ی بیرونی را می‌شکند؛ نشت مدل دامنه به قرارداد عمومی.
- **بدون رویداد** — رد شد: معماری event-driven چالش (outbox) بی‌معنا می‌شد و گسترش‌پذیری بعدی (audit، notify) به دامنه نشت می‌کرد.

## پیامدها

### مثبت

- دامنه از جزئیات انتشار پاک می‌ماند؛ قرارداد بیرونی versionable و پایدار است.
- انتشار Integration Event از طریق Outbox (ADR-0010) به Kafka (ADR-0027) انجام می‌شود.

### منفی / بدهی فنی

- نگاشت DomainEvent → IntegrationEvent کد اضافه‌ای است که باید در adapter نگه داشته و تست شود.
