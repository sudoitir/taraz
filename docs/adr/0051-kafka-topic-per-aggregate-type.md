# 0051. توپولوژی Kafka: یک topic برای هر نوع aggregate (تنگ‌کردن ADR-0027)

**وضعیت:** پذیرفته‌شده

**تاریخ:** ۲۰۲۶-۰۸-۱۹

## زمینه

متن ADR-0027 می‌گوید «topicها بر اساس نوع رویداد تعریف می‌شوند» — یعنی یک topic جدا برای
`account.credited`، یکی برای `account.debited` و غیره. کار طراحی این تغییر نشان داد این طراحی
ترتیب رویدادهای یک حساب را می‌شکند: اگر credit و debit یک حساب روی دو topic جدا باشند، Kafka فقط
داخل یک partition از **یک** topic ترتیب می‌دهد؛ مصرف‌کننده‌ای که موجودی را از روی stream بازسازی
می‌کند نمی‌تواند بفهمد کدام‌یک زودتر رخ داده. این یک تعارض واقعی با یک ADR پذیرفته‌شده است و باید
صریح ثبت شود، نه بی‌سروصدا دور زده شود.

## تصمیم

توپولوژی: **یک topic برای هر نوع aggregate**، نه هر نوع رویداد:

- `taraz.account.v1` — `account.opened`, `account.credited`, `account.debited`، partition key
  `account_id`.
- `taraz.transaction.v1` — `transaction.posted`, `transaction.compensated`، partition key
  `transaction_id`.

هر رویدادی که یک حساب را نام می‌برد روی همان یک topic، keyed به همان حساب، منتشر می‌شود — پس همه‌ی
رویدادهای یک حساب روی یک partition و به ترتیب commit قرار می‌گیرند. `transaction.posted` برای یک
transfer دو حساب را نام می‌برد و به همین دلیل کلید طبیعی‌اش تراکنش است، نه یکی از دو حساب.

این ADR متن ADR-0027 را **تنگ می‌کند**: «per event type» با «per aggregate type» جایگزین می‌شود،
با استدلال حفظ ترتیب که در بالا آمد.

## گزینه‌های بررسی‌شده

- **یک topic برای هر نوع رویداد (متن لفظی ADR-0027)** — رد شد: ترتیب رویدادهای یک حساب را می‌شکند؛
  هیچ مصرف‌کننده‌ای نمی‌تواند بدون merge کردن چند topic بر اساس timestamp (که زیر at-least-once و
  clock skew شکننده است) ترتیب واقعی را بازسازی کند.

## پیامدها

### مثبت

- ترتیب رویدادهای هر حساب برای مصرف‌کننده‌ای که از یک partition می‌خواند تضمین می‌شود.

### منفی / بدهی فنی

- ترتیب انتشار بین‌instance فقط برای یک poller تک‌نمونه‌ای تضمین می‌شود (ADR-0055)؛ scale-out افقی
  poller نیازمند یک طراحی جدید (partition بر اساس key) است که در این تغییر پیاده نشده.
