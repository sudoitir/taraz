# 0027. Kafka به‌عنوان broker رویدادهای integration

**وضعیت:** پذیرفته‌شده
**تاریخ:** ۲۰۲۶-۰۸-۱۸

## زمینه

رویدادهای integration (ADR-0009) از طریق outbox (ADR-0010) باید به بیرون از مرز سرویس منتشر شوند تا مصرف‌کننده‌های دیگر (audit، notify، reporting) بدون coupling به دیتابیس داخلی از وقایع مالی باخبر شوند. چالش اجازه‌ی Kafka را صریحاً داده و هر infra اختیاری باید با مسئله‌ی واقعی توجیه شود: مسئله‌ی واقعی این‌جا «انتشار پایدار و قابل‌مصرف‌مجدد رویدادهای مالی به چند مصرف‌کننده‌ی مستقل» است.

## تصمیم

**Apache Kafka** به‌عنوان broker انتشار Integration Eventها؛ producer همان polling publisherِ outbox است (ADR-0010) و topicها بر اساس نوع رویداد تعریف می‌شوند.

## گزینه‌های بررسی‌شده

- **بدون broker (log/no-op consumer)** — رد شد: انتشار واقعی رخ نمی‌دهد؛ معماری event-driven فقط روی کاغذ می‌ماند.
- **RabbitMQ** — رد شد: برای کاربرد event-log مالی، مدل log-based ماندگار Kafka (replay، چند مصرف‌کننده‌ی مستقل روی یک stream) مناسب‌تر از صف پیام‌محور است.
- **HTTP webhook مستقیم** — رد شد: coupling زمان‌اجرا به مصرف‌کننده؛ خرابی طرف مقابل انتشار را می‌خواباند.

## پیامدها

### مثبت

- رویدادهای مالی پایدار و قابل‌replay برای مصرف‌کننده‌های حاضر و آینده؛ جداسازی کامل تولیدکننده از مصرف‌کننده.

### منفی / بدهی فنی

- **زیرساخت سوم** با هزینه‌ی عملیاتی واقعی (cluster، monitoring) — آگاهانه پذیرفته شده چون مسئله‌ی مشخص بالا را حل می‌کند؛ در docker-compose توسعه (ADR-0025) و Testcontainers یکپارچه می‌شود.
- at-least-once از outbox تا مصرف‌کننده ادامه دارد؛ idempotency سمت مصرف‌کننده الزامی باقی می‌ماند.
