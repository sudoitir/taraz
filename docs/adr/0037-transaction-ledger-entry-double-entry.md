# 0037. Aggregate دوم: Transaction با LedgerEntryهای double-entry

**وضعیت:** پذیرفته‌شده

**تاریخ:** ۲۰۲۶-۰۸-۱۸

## زمینه

دامنه‌ی تراز به یک مدل تراکنش نیاز دارد که هم audit کامل بدهد و هم invariant «مبلغ کسرشده از مبدأ دقیقاً برابر مبلغ افزوده‌شده به مقصد» را ساختاری تضمین کند. سوال کلیدی: آیا همه‌ی تراکنش‌ها باید double-entry کامل باشند (یعنی مجموع legs همیشه صفر)؟ برای `credit`/`DEBIT` تک‌طرفه این ممکن نیست مگر با یک حساب داخلی فرضی به‌عنوان طرف مقابل همه‌ی تراکنش‌ها.

## تصمیم

- `Transaction` یک aggregate root دوم و کاملاً immutable است که `LedgerEntry`های خودش را مالک است؛ هر entry یک جهت (`DEBIT`/`CREDIT`)، یک account و یک مبلغ دارد.
- شکل legs از روی نوع تراکنش اجبار می‌شود:
  - `TRANSFER`: دقیقاً دو leg — یک `DEBIT` روی مبدأ و یک `CREDIT` روی مقصد، با مبالغ برابر؛ مجموع خالص **صفر** است و همین‌جا enforce می‌شود.
  - `CREDIT`: دقیقاً یک leg از نوع `CREDIT` (پول از بیرون سرویس وارد می‌شود).
  - `DEBIT`: دقیقاً یک leg از نوع `DEBIT` (پول از سرویس خارج می‌شود).
- invariant صفرشدن مجموع فقط برای `TRANSFER` تعریف می‌شود؛ حساب clearing سراسری **رد می‌شود** (پایین).
- واحد atomic یک command از دو aggregate `Account` + یک `Transaction` تشکیل می‌شود — خروج آگاهانه از قاعده‌ی «یک transaction دیتابیسی = یک aggregate» که با ADR-0018 و ADR-0026 توجیه می‌شود: lock روی ردیف‌های account به ترتیب `accountId` گرفته می‌شود و هر سه در همان transaction دیتابیس persist می‌شوند.
- جبران (ADR-0035) با `compensationOf` یک transaction جدید می‌سازد که جهت همه‌ی legs معکوس شده و به تراکنش اصلی لینک است؛ تراکنش اصلی دست‌نخورده می‌ماند. یک پیاده‌سازی واحد هر سه حالت جبران را پوشش می‌دهد و ساختاری است که نمی‌تواند reversal نامتعادل بسازد.

## گزینه‌های بررسی‌شده

- **رکورد تراکنش تخت با source/destination nullable** — رد شد: شکل nullable به‌جای مدل، invariantها را از نوع‌داده به if پراکنده منتقل می‌کرد و audit پای legها را حذف می‌کرد.
- **حساب clearing داخلی برای متوازن کردن همه‌ی تراکنش‌ها** — رد شد: آن یک ردیف طرف مقابل همه‌ی credit/debitها می‌شود و زیر lockهای pessimistic ردیفی ADR-0026 همه‌ی accountهای مستقل را پشت هم سریالیزه می‌کند — نقض مستقیم قانون چالش «accountهای مستقل نباید بدون دلیل یکدیگر را block کنند».
- **فقط ذخیره‌ی خالص اثر روی balance بدون legs** — رد شد: نه audit دارد نه راهی برای enforce کردن برابری دو طرف transfer.

## پیامدها

### مثبت

- برابری مبلغ دو طرف transfer ساختاری تضمین می‌شود؛ audit trail کامل؛ جبران برای هر سه نوع عملیات با یک مسیر واحد؛ حساب‌های مستقل هیچ‌وقت پشت یک ردیف داغ مشترک قفل نمی‌شوند.

### منفی / بدهی فنی

- aggregate دوم و موجودیت فرزند به مدل اضافه می‌شود؛ persistence باید دو جدول (transaction + ledger_entry) را مدیریت کند؛ واحد atomic بزرگ‌تر از یک aggregate است و درستی‌اش به ترتیب lock در ADR-0026 وابسته می‌ماند.
