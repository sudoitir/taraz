# 0010. الگوی Outbox برای انتشار رویداد

**وضعیت:** پذیرفته‌شده
**تاریخ:** ۲۰۲۶-۰۸-۱۸

## زمینه

ثبت تغییر موجودی در PostgreSQL و انتشار رویداد به Kafka دو سیستم مستقل‌اند؛ dual-write کلاسیک بین آن‌ها اتمیک نیست — crash بین commit و publish یعنی رویداد گمشده، و publish قبل از commit یعنی رویدادِ تراکنشِ rollback‌شده. هیچ‌کدام برای یک سرویس مالی قابل‌قبول نیست.

## تصمیم

**الگوی Outbox**: Integration Event در همان تراکنش دیتابیسِ تغییر حالت (مرز تراکنش طبق ADR-0018) در جدول `outbox` ثبت می‌شود؛ پس اتمیسیته «تغییر حالت + رویداد» را خودِ تراکنش دیتابیس تضمین می‌کند.

انتشار به Kafka توسط یک **polling publisher** درون‌اپلیکیشن انجام می‌شود: ردیف‌های unpublished را با lock (`FOR UPDATE SKIP LOCKED`) می‌خواند، produce می‌کند و published علامت می‌زند.

## گزینه‌های بررسی‌شده

- **Dual-write مستقیم (DB + Kafka در کد)** — رد شد: اتمیک نیست؛ سناریوی crash بین دو write قابل‌رفع نیست.
- **Debezium CDC از روی WAL** — رد شد: latency نزدیک به صفر ولی یک Kafka Connect cluster اضافه می‌کند؛ برای مقیاس چالش over-engineering است.
- **انتشار sync به Kafka در همان request** — رد شد: coupling زمان‌اجرا به broker؛ خرابی Kafka عملیات مالی را می‌خواباند.

## پیامدها

### مثبت

- رویداد هرگز بدون تغییر حالت (و بالعکس) منتشر نمی‌شود؛ مصالحه‌ی صریح با چالش consistency.

### منفی / بدهی فنی

- حداقل یک‌بار تحویل (at-least-once) — مصرف‌کننده باید idempotent باشد.
- تأخیر انتشار به‌اندازه‌ی بازه‌ی polling؛ جدول outbox به پاک‌سازی دوره‌ی ردیف‌های published نیاز دارد.
