# 0035. سرویس جبران (compensate) برای هر سرویس

**وضعیت:** پذیرفته‌شده

**تاریخ:** ۲۰۲۶-۰۸-۱۸

## زمینه

در سیستم مالی، عملیات‌ها گاهی باید خنثی شوند: اشتباه اپراتور، reversal تراکنش، یا جبران یک گردش‌کار چندمرحله‌ای که در میانه شکست خورده. اگر جبران به‌صورت موردی و پراکنده پیاده شود، معنای «خنثی‌سازی» برای هر use case متفاوت و audit trail ناقص می‌شود.

## تصمیم

- **هر command handler یک handler جبران متناظر دارد** (`compensate`) در همان لایه‌ی application service:
  - `credit` ↔ `compensateCredit` (debit معکوس با همان مبلغ)
  - `debit` ↔ `compensateDebit` (credit معکوس)
  - `transfer` ↔ `compensateTransfer` (انتقال معکوس از مقصد به مبدأ)
- جبران یک **عملیات مالی جدید با transactionId خودش** است، نه حذف یا rollback رکورد قبلی. رکورد اصلی دست‌نخورده می‌ماند و اثر معکوس به‌عنوان تراکنش مستقل ثبت می‌شود — audit کامل حفظ می‌شود.
- جبران همان invariantها را رعایت می‌کند: idempotency با transactionId خودش (طبق ADR-0034)، عدم موجودی منفی، atomicity در transfer.
- جبرانِ یک transactionId که هرگز اعمال نشده، خطای دامنه است (نمی‌توان چیزی را که وجود ندارد خنثی کرد).
- API عمومی جبران (endpoint) در scope فعلی چالش نیست؛ قرارداد inbound port تعریف می‌شود و HTTP exposure در تغییر مربوط به خودش می‌آید.

## گزینه‌های بررسی‌شده

- **Rollback با حذف رکورد اصلی** — رد شد: در سیستم مالی هیچ رکوردی حذف نمی‌شود؛ audit trail باید کامل بماند.
- **جبران موردی فقط برای transfer** — رد شد: قاعده‌ی یکدست «هر سرویس یک compensate دارد» ساده‌تر و قابل پیش‌بینی‌تر است.
- **Saga orchestrator مجزا** — رد شد: در scope یک سرویس تک‌ماژوله بیش از حد است؛ قرارداد compensate زمینه‌ی saga آینده را فراهم نگه می‌دارد.

## پیامدها

### مثبت

- رفتار خنثی‌سازی برای همه‌ی عملیات‌ها یکدست و قابل audit است؛ reversal بدون دست‌کاری تاریخچه ممکن می‌شود.

### منفی / بدهی فنی

- سه handler اضافه و تست‌های متناظرشان؛ باید مراقب بود compensate خودش نیز idempotent بماند و زنجیره‌ی جبرانِ جبران (compensate of compensate) معنای مشخص داشته باشد — فعلاً فقط جبرانِ عملیات اصلی مجاز است.
