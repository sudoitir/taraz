# 0054. اندازه‌گذاری Hikari + open-in-view: false به‌عنوان مکانیزم backpressure

**وضعیت:** پذیرفته‌شده

**تاریخ:** ۲۰۲۶-۰۸-۱۹

## زمینه

`spring.jpa.open-in-view` امروز تنظیم نشده (پیش‌فرض `true`) — زیر virtual threadها و یک استخر
Hikari محدود، این یعنی یک connection برای کل عمر request (حتی رندر view) نگه داشته می‌شود. با
۱۰۰۰ virtual thread هم‌زمان در برابر یک استخر کوچک، این یک deadlock ناشی از starvation **نامرئی**
است — بدون متریک، بدون رد صریح، فقط latency که رشد می‌کند.

## تصمیم

- `spring.jpa.open-in-view: false`.
- استخر Hikari ثابت (`maximum-pool-size == minimum-idle`)، اندازه‌گذاری‌شده در برابر
  `max_connections` واقعی PostgreSQL، نه در برابر concurrency درخواست — ظرفیت واقعی از تراکنش‌های
  کوتاه می‌آید (ADR-0018/0026)، نه از استخر بزرگ‌تر.
- `connection-timeout` کوتاه (~۲ ثانیه) تا اتمام استخر به‌جای صف نامرئی، خطای typed
  `CONCURRENCY_CONFLICT` → ۵۰۳ بدهد (ADR-0048).

## گزینه‌های بررسی‌شده

- **استخر بزرگ‌تر برای جذب همه‌ی virtual threadها** — رد شد: connection یک منبع محدودِ سمت
  دیتابیس است؛ بزرگ‌کردن استخر فقط contention را به داخل PostgreSQL منتقل می‌کند، آن را حل
  نمی‌کند.
- **رها کردن `open-in-view` روی پیش‌فرض** — رد شد: دقیقاً همان ریسک نامرئی که این ADR می‌بندد.

## پیامدها

### مثبت

- اتمام ظرفیت یک سیگنال typed و قابل‌اندازه‌گیری می‌شود، نه یک صف پنهان.

### منفی / بدهی فنی

- زیر بار خیلی بالاتر از اندازه‌ی استخر، کلاینت‌ها `503` می‌بینند به‌جای انتظار طولانی — یک
  trade-off آگاهانه به نفع قابل‌پیش‌بینی‌بودن.
